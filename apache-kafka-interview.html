QUESTION 1
🔹 What is Apache Kafka and why is it popular?
💡 Quick Definition
Apache Kafka is a distributed event-streaming platform originally built at LinkedIn (2011, open-sourced). It acts as a high-throughput, fault-tolerant, durable message broker + storage system + stream-processing platform — all in one.
✨ One-liner: Kafka is a "central nervous system for data" — capturing, storing, and distributing events across an entire organization in real time.
📰 Analogy: Think of Kafka as a giant newspaper distribution system. Newspapers (messages) are published into different sections (topics). Many readers (consumers) can subscribe to the sections they care about, read at their own pace, and even re-read old issues because the newspaper archive is preserved. New readers can arrive years later and start reading from page one — Kafka keeps the history.
🌟 Why is Kafka So Popular?
1 Massive Throughput
Handles millions of messages per second on commodity hardware. LinkedIn processes 7+ trillion messages a day.
2 Durable Storage
Messages are written to disk and replicated. Configurable retention (hours, days, forever). Acts as a "replayable log".
3 Distributed & Fault-Tolerant
Runs on a cluster of brokers. Partitions are replicated — if one broker dies, others take over seamlessly.
4 Decouples Producers & Consumers
Producers don't know consumers; consumers don't know producers. Add new consumers anytime — the data is already stored.
5 Real-Time Streaming
Sub-millisecond latency. Powers fraud detection, real-time analytics, recommendation engines.
6 Rich Ecosystem
Kafka Connect (integrations), Kafka Streams (processing), Schema Registry, KSQL — a complete platform.
🎯 Real-World Examples
🔹 LinkedIn — activity tracking, log aggregation (Kafka's birthplace)
🔹 Netflix — real-time analytics, recommendation pipeline
🔹 Uber — geo-location streaming, dispatch system
🔹 Airbnb — event-driven microservice communication
🔹 Banks — fraud detection, transaction streaming
CLOSING HOOK
"Kafka isn't just a message queue — it's a distributed, durable, replayable event log. That's why it became the backbone of modern event-driven architectures. 'Where data lives, Kafka flows.'"
🧠 Key Phrases to Drop
Distributed event-streaming platform Replayable, durable log Decouples producers and consumers Trillion-message scale Central nervous system for data
QUESTION 2
🔹 Kafka vs Traditional Message Queues (RabbitMQ, ActiveMQ)
💡 Purpose
Both Kafka and traditional message queues let services exchange messages — but they work in fundamentally different ways:

🔹 RabbitMQ / ActiveMQ = traditional brokers — push-based, route & deliver, then forget
🔹 Kafka = a distributed log — pull-based, store messages even after consumption, optimized for huge throughput
✨ RabbitMQ = post office (deliver and discard). Kafka = library (deliver and keep).
📚 Analogy: RabbitMQ is like a post office — it delivers your letter to the recipient and the letter is gone. Kafka is like a library — books (messages) stay on the shelf; many readers can come and read the same book independently, even years later.
📊 Side-by-Side Comparison
┌──────────────────────┬────────────────────────┬──────────────────────────┐
│ Aspect               │ RabbitMQ / ActiveMQ    │ Kafka                    │
├──────────────────────┼────────────────────────┼──────────────────────────┤
│ Storage model        │ Queue (FIFO, deleted)  │ Append-only log (kept)   │
│ Delivery model       │ Push to consumer       │ Consumer pulls           │
│ Throughput           │ Tens of thousands/sec  │ Millions/sec             │
│ Replay capability    │ ❌ No                  │ ✅ Yes (offset rewind)    │
│ Multiple consumers   │ Each msg → 1 consumer  │ Same msg → N consumers   │
│ Routing complexity   │ ✅ Rich (exchanges)    │ ❌ Simple (topics)        │
│ Ordering guarantee   │ Per queue              │ Per partition            │
│ Storage size         │ Typically small        │ Terabytes to petabytes   │
│ Best use case        │ Task queues, RPC       │ Event streaming, logs    │
└──────────────────────┴────────────────────────┴──────────────────────────┘
🎯 When to Use Which
✅ RabbitMQ wins when...
Complex routing rules, low-volume task queues, request-reply patterns, when each message has exactly one consumer (e.g., job processing).
✅ Kafka wins when...
High throughput, event sourcing, log aggregation, multiple independent consumers reading the same stream, replay/audit needs, real-time analytics.
CLOSING HOOK
"Don't think 'Kafka vs RabbitMQ' — think 'event log vs message queue.' RabbitMQ delivers and forgets. Kafka delivers and remembers. Pick based on whether you need replayability and multi-consumer streams."
🧠 Key Phrases to Drop
Append-only distributed log Pull-based vs push-based Replayability Multi-consumer streaming
QUESTION 3
🔹 Core Kafka Architecture & Components
💡 Quick Definition
Kafka has a small set of well-defined components that, working together, give it its scalability, durability, and fault-tolerance.
✨ Producer → Topic (partitions) → Broker (cluster) → Consumer Group. That's Kafka in one line.
🏛️ The Core Components
1 Producer
Application that publishes (writes) messages to Kafka topics.
2 Consumer
Application that subscribes (reads) messages from topics.
3 Broker
A single Kafka server. Stores partitions, handles producer/consumer requests.
4 Cluster
A group of brokers working together. Provides scalability & fault tolerance.
5 Topic
A logical category/feed for messages (e.g., orders, payments, clicks).
6 Partition
A topic is split into partitions — each is an ordered, immutable sequence (a log file). Enables parallelism.
7 Offset
A unique, sequential ID for each message within a partition. Tells consumers what they've read.
8 Consumer Group
A group of consumers sharing the work of reading from a topic — each partition is consumed by exactly one consumer in the group.
9 Zookeeper / KRaft
Coordinates brokers — leader election, metadata, configuration. KRaft (Kafka Raft) is the modern Zookeeper-less replacement.

      │ Consumer │         │ Consumer │
      │  Group X │         │  Group Y │
      └──────────┘         └──────────┘
CLOSING HOOK
"Kafka's elegance: just 4 actors (Producer, Broker, Topic, Consumer) and 2 concepts (Partition, Offset) — but combined, they deliver internet-scale streaming. Master these 6 terms and you've mastered 80% of Kafka."
🧠 Key Phrases to Drop
Producers, brokers, consumers, topics, partitions Append-only log per partition Consumer groups for parallelism Zookeeper or KRaft for coordination
QUESTION 4
🔹 What is a Topic and a Partition?
💡 Quick Definition
🔹 Topic = a logical name/category for a stream of messages (e.g., orders, user-signups, page-views).

🔹 Partition = a topic is internally split into one or more partitions. Each partition is an ordered, immutable sequence of messages stored as a log on disk.
✨ Topic = a folder. Partitions = files inside that folder. Each file is append-only.
📰 Analogy: Imagine a newspaper called "Sports News" (the topic). To meet huge demand, the publisher prints it across 3 separate printing presses (the partitions) running in parallel. Each press produces its own ordered stack of papers. Three readers can read simultaneously, one per press.
🌟 Why Partitions Matter
1 Parallelism
Producers can write to multiple partitions concurrently. Consumers in a group can read multiple partitions concurrently.
2 Scalability
More partitions = more throughput. Partitions can be spread across many brokers.
3 Ordered within Partition
Messages in a single partition are strictly ordered. Across partitions, order is NOT guaranteed.
4 Replication Unit
Each partition is replicated across multiple brokers — that's how Kafka achieves fault tolerance.
🔑 How Producers Pick a Partition
🔹 If a key is set (e.g., userId) → Kafka uses hash(key) % numPartitions. Same key always goes to the same partition (preserving order per user).
🔹 If no key → round-robin (or "sticky" partitioner since 2.4) for even distribution.
🔹 Custom partitioner — you can implement your own.
⚠️ Important Trade-offs
🔹 More partitions = more parallelism but also more open file handles, more rebalancing time, more end-to-end latency.
🔹 Order is per-partition, not per-topic. If you need strict ordering, route related events to the same partition (using a key).
🔹 Partitions can be added but not removed. Plan capacity upfront.
CLOSING HOOK
"Partitions are the unit of parallelism, the unit of ordering, and the unit of replication in Kafka. Choose partition count wisely — it directly determines your max throughput and consumer parallelism."
🧠 Key Phrases to Drop
Topic = logical, Partition = physical Ordered within partition only Same key → same partition Partition = unit of parallelism
QUESTION 5
🔹 What is an Offset in Kafka?
💡 Quick Definition
An offset is a unique, sequential, ever-increasing integer ID assigned to each message within a partition. It identifies the position of a message in the log — like a line number in a file.
✨ Offset = "bookmark" — tells the consumer "I've read up to message #154 in partition 2."
📖 Analogy: Imagine reading a long e-book. Your Kindle remembers "page 154" — that's the offset. Even if you close the book and come back tomorrow, you resume from page 154. In Kafka, the offset is the consumer's bookmark per partition.
📦 How Offsets Work
Partition 0:  [msg:0] [msg:1] [msg:2] [msg:3] [msg:4] [msg:5]
Partition 1:  [msg:0] [msg:1] [msg:2] [msg:3]
Partition 2:  [msg:0] [msg:1] [msg:2] [msg:3] [msg:4]

Consumer's offset state:
  Partition 0 → committed offset: 4 (next read = 5)
  Partition 1 → committed offset: 2 (next read = 3)
  Partition 2 → committed offset: 0 (next read = 1)
🌟 Key Properties
1 Per-Partition
Each partition has its own independent offset sequence. msg:5 in partition 0 has nothing to do with msg:5 in partition 1.
2 Immutable & Monotonic
Offsets always increase. They're never reused, never rewritten.
3 Consumer-Tracked
Each consumer tracks its own offsets per partition. Two different consumer groups read independently.
4 Stored in __consumer_offsets
Kafka stores committed offsets in a special internal topic — so consumers can resume after restart.
🔑 Special Offset Values
🔹 auto.offset.reset = earliest — read from beginning if no committed offset
🔹 auto.offset.reset = latest — read only new messages (default)
🔹 auto.offset.reset = none — throw exception if no committed offset
CLOSING HOOK
"Offsets are Kafka's secret to replayability. Want to reprocess yesterday's data? Reset the offset. Want a new consumer to start from scratch? Use earliest. 'The offset is the bookmark, and Kafka never loses your bookmark.'"
🧠 Key Phrases to Drop
Per-partition sequential ID Stored in __consumer_offsets topic auto.offset.reset Replay by rewinding offset
QUESTION 6
🔹 Producer & Consumer — Basics
💡 Quick Definition
🔹 Producer — an app that publishes (writes) messages to one or more topics. Decides which partition to send each message to.

🔹 Consumer — an app that subscribes (reads) messages from one or more topics, tracks its progress via offsets.
✨ Producer = the writer. Consumer = the reader. Kafka = the durable bookshelf in between.
📤 The Producer
🔹 Sends a ProducerRecord = (topic, key, value, optional partition, optional timestamp)
🔹 Internally batches messages for efficiency
🔹 Compresses batches (gzip, snappy, lz4, zstd)
🔹 Waits for acknowledgment from broker (acks=0/1/all)
🔹 Retries on failure with optional idempotence (no duplicates)
🔹 Async by default — returns a Future / callback
📥 The Consumer
🔹 Subscribes to one or more topics (or assigns specific partitions)
🔹 Continuously polls() the broker for new records
🔹 Joins a Consumer Group to share work with other consumers
🔹 Tracks offsets per partition; commits them periodically (or manually)
🔹 Handles rebalancing when consumers join/leave the group
🔹 Pull-based — consumer controls the pace (no overload)
🛠️ Spring Kafka Example (Java)
// Producer
@Autowired
private KafkaTemplate<String, Order> kafkaTemplate;

public void publish(Order o) {
    kafkaTemplate.send("orders", o.getId(), o);
}

// Consumer
@KafkaListener(topics = "orders", groupId = "order-processor")
public void consume(Order order) {
    log.info("Received: {}", order);
}
CLOSING HOOK
"Producers and consumers are decoupled in time AND space — they don't need to be online together, and they don't even need to know each other exists. Kafka is the durable buffer in between. 'Write fast, read at your own pace.'"
🧠 Key Phrases to Drop
ProducerRecord = topic + key + value Pull-based consumer (poll loop) Decoupled in time and space Batching + compression for throughput
QUESTION 7
🔹 What is a Consumer Group and why is it important?
💡 Quick Definition
A Consumer Group is a set of consumers that share the work of reading from a topic. Kafka assigns each partition to exactly one consumer within the group — never two from the same group consume the same partition simultaneously.
✨ Consumer Group = teamwork. The work (partitions) is divided fairly among teammates (consumers).
📦 Analogy: Imagine 3 mailboxes (partitions) in a building and 3 mail-carriers (consumers in one group) — each carrier takes one mailbox. If a 4th carrier joins, they sit idle (no extra mailbox). If one carrier leaves, the remaining 2 split the 3 mailboxes again. Different groups are like different delivery companies — each gets the full set of mailboxes independently.
🎯 Why Consumer Groups Matter
1 Horizontal Scaling
Add more consumers to the group → work spreads automatically. Up to N consumers per group, where N = number of partitions.
2 Fault Tolerance
If a consumer crashes, its partitions are reassigned to other group members within seconds (rebalancing).
3 Independent Streams
Multiple groups can subscribe to the same topic. Each group reads independently — at its own pace, with its own offsets.
4 Load Balancing
Kafka automatically distributes partitions evenly across the group.
⚠️ Important Rules
🔹 Each partition → exactly one consumer in a group. (One-to-one.)
🔹 One consumer can handle multiple partitions. (One-to-many.)
🔹 If consumers > partitions, the extras are idle.
🔹 Different groups read the SAME data INDEPENDENTLY. (Pub-sub semantics.)
🎨 Visual
Topic "orders" with 4 partitions

         Partitions: P0, P1, P2, P3

Group A (3 consumers):
  ConsumerA1 → P0, P3
  ConsumerA2 → P1
  ConsumerA3 → P2

Group B (4 consumers):              ← reads SAME data, independently
  ConsumerB1 → P0
  ConsumerB2 → P1
  ConsumerB3 → P2
  ConsumerB4 → P3
CLOSING HOOK
"Consumer groups give Kafka its 'best of both worlds' behavior — within a group, it's a queue (each message processed once). Across groups, it's pub-sub (every group sees everything). 'Same topic, many independent readers.'"
🧠 Key Phrases to Drop
Each partition → one consumer per group Horizontal scaling via group members Multiple groups = pub-sub Max parallelism = partition count
QUESTION 8
🔹 What is a Broker and a Kafka Cluster?
💡 Quick Definition
🔹 Broker = a single Kafka server. Holds partitions, accepts producer writes, serves consumer reads.

🔹 Cluster = a group of brokers working together. Provides scalability and fault tolerance.
✨ Broker = one machine. Cluster = the team of machines that act as one giant Kafka.
🏛️ How Brokers Work in a Cluster
🔹 Each broker has a unique broker ID.
🔹 A topic's partitions are spread across brokers for load distribution.
🔹 Each partition has a leader broker (handles all reads/writes) and follower brokers (replicas).
🔹 If a broker fails, partition leaders are elected on other brokers automatically — no downtime.
🔹 Brokers coordinate via Zookeeper (or KRaft in modern Kafka).
🛡️ The Controller Broker
One broker in the cluster is elected as the Controller. Its job:
🔹 Maintains cluster metadata (which broker holds what)
🔹 Manages partition leader election
🔹 Handles broker join/leave events

If the controller dies, another broker is elected automatically.
🌟 Why Multiple Brokers?
1 Scalability
Add brokers → spread partitions → more throughput. Linear horizontal scaling.
2 Fault Tolerance
Each partition is replicated across brokers. Lose one broker, no data lost.
3 Geographic Distribution
Brokers can span data centers (multi-DC setups via MirrorMaker).
📊 Typical Cluster Sizes
🔹 Small (dev/test) — 1 broker (no fault tolerance)
🔹 Production minimum — 3 brokers (RF=3 for safety)
🔹 Medium prod — 5–10 brokers
🔹 Large (LinkedIn, Uber) — 100s to 1000s of brokers per cluster
CLOSING HOOK
"A Kafka cluster is just brokers + coordination. Each broker stores some partitions, leads some partitions, follows others. Cluster size scales linearly with your throughput needs. 'Distribute partitions, replicate for safety, scale brokers for speed.'"
🧠 Key Phrases to Drop
Broker = single Kafka server Controller broker for metadata Linear horizontal scaling Replication across brokers
QUESTION 9
🔹 Role of Zookeeper & the KRaft Replacement
💡 Quick Definition
Historically, Kafka used Apache Zookeeper — a separate distributed coordination service — to manage cluster metadata, leader election, and broker discovery. Modern Kafka (3.3+) supports KRaft mode (Kafka Raft) — Zookeeper-less, simpler, faster.
✨ Zookeeper used to be Kafka's "brain". KRaft moves the brain INSIDE Kafka.
🐘 What Zookeeper Did (Old Way)
🔹 Cluster metadata — list of brokers, topics, partitions, leaders
🔹 Controller election — picks one broker as the controller
🔹 Broker membership — heartbeats; detects broker failures
🔹 Configuration — topic/broker configs
🔹 ACLs — security rules (early versions)
😩 Problems with Zookeeper
🔹 Operational overhead — deploy, secure, monitor a separate service
🔹 Scalability limits — Zookeeper struggled at huge metadata scale
🔹 Complex failure modes — Zookeeper down = Kafka in trouble
🔹 Slow controller failover — could take seconds
🔹 Two systems to learn for new operators
⚡ KRaft Mode (the Future)
KRaft = Kafka Raft Metadata. Kafka's own brokers manage metadata using the Raft consensus algorithm — no Zookeeper needed.

🔹 Status: production-ready since Kafka 3.3 (2022). Zookeeper deprecated.
🔹 Simpler ops — only one system to deploy & secure
🔹 Faster controller failover — milliseconds instead of seconds
🔹 Scales to millions of partitions per cluster
🔹 Faster startup for huge clusters
🔄 The Architecture Difference
OLD (Zookeeper):
  ┌──────────────┐     ┌────────────────┐
  │  Zookeeper   │ ←→  │ Kafka Brokers  │
  │   Ensemble   │     │   (Cluster)    │
  └──────────────┘     └────────────────┘

NEW (KRaft):
  ┌────────────────────────────────────┐
  │   Kafka Brokers (with Controllers) │
  │   Self-managed via Raft consensus  │
  └────────────────────────────────────┘
CLOSING HOOK
"Zookeeper is being phased out. If you start a new Kafka project today, use KRaft. If you maintain an old cluster, plan a migration. 'One less moving part = less ops pain.'"
🧠 Key Phrases to Drop
Zookeeper-less Kafka via KRaft Raft consensus for metadata Faster controller failover Scales to millions of partitions
QUESTION 10
🔹 Replication, Leader, Follower & ISR
💡 Quick Definition
Kafka achieves fault tolerance via partition replication. Each partition has multiple copies (replicas) on different brokers — one is the leader, the rest are followers. The set of replicas that are caught up with the leader is called the ISR (In-Sync Replicas).
✨ Replication factor 3 = 3 copies. One leader, two followers. Lose any 1, you're safe.
📰 Analogy: Like having multiple printing presses for the same newspaper. The "lead" press prints first; "follower" presses copy each issue. If the lead breaks, a follower is promoted to lead — no missed issues.
🏛️ Roles Explained
👑 Leader
Handles ALL reads and writes for the partition. There is exactly one leader per partition at any time.
📋 Follower
Continuously fetches new messages from the leader. Doesn't serve clients directly. Acts as a hot standby.
✅ ISR (In-Sync Replicas)
The set of replicas (leader + caught-up followers) that are within replica.lag.time.max.ms of the leader. Only ISR members can be promoted to leader.
⚠️ Out-of-Sync Replica
A follower that's lagging behind. Removed from ISR until it catches up.
🔄 What Happens on Broker Failure?
1️⃣ Broker holding a partition leader crashes
2️⃣ Controller detects failure (heartbeat timeout)
3️⃣ Controller picks an ISR member as new leader
4️⃣ Producers/consumers redirect to the new leader
5️⃣ When the failed broker recovers, it rejoins as a follower & catches up
⚙️ Important Configurations
🔹 replication.factor — number of replicas per partition (typically 3 in prod)
🔹 min.insync.replicas — minimum ISR size before producer can write (with acks=all). Typically 2 with RF=3.
🔹 unclean.leader.election.enable — if true, allows out-of-sync replica to become leader (data loss risk). Default: false.
🛡️ Best Practice for Production
replication.factor      = 3
min.insync.replicas     = 2
acks                    = all
unclean.leader.election = false
This combination ensures: a write is acknowledged only when stored on at least 2 of 3 replicas. You can tolerate 1 broker failure with zero data loss.
CLOSING HOOK
"Replication is the heart of Kafka's durability. 'Leaders serve, followers replicate, ISR is the safety net.' Tune RF + acks + min.insync.replicas together — they form the durability triangle."
🧠 Key Phrases to Drop
Leader-Follower replication ISR = In-Sync Replicas RF=3, min.insync.replicas=2, acks=all Unclean leader election (avoid in prod)
QUESTION 11
🔹 Producer Acknowledgments (acks=0/1/all)
💡 Quick Definition
The acks setting controls how many brokers must acknowledge a producer's write before the producer considers the message "successfully sent." It's the most important durability vs throughput trade-off in Kafka.
✨ acks=0 → fastest, riskiest. acks=1 → balanced. acks=all → safest, slowest.
📊 The 3 Acknowledgment Modes
0 acks=0 — Fire & Forget
Producer doesn't wait for any ack. Sends and moves on.
✅ Fastest (highest throughput, lowest latency)
❌ Risky — if broker dies before message lands, data is lost
🎯 Use for: metrics, telemetry, log streams (where loss is acceptable)
1 acks=1 — Leader Only (default)
Producer waits for leader broker to acknowledge.
✅ Balanced — fast and reasonably safe
❌ Edge-case loss — if leader dies AFTER ack but BEFORE replication, data lost
🎯 Use for: most general use cases (default)
∞ acks=all (or -1) — All ISRs
Producer waits until ALL in-sync replicas acknowledge.
✅ Strongest durability — no data loss as long as at least min.insync.replicas survive
❌ Slower — full replication latency
🎯 Use for: financial transactions, audit logs, anything you can't lose
📊 Quick Comparison
┌────────┬────────────┬──────────────────┬────────────────────────┐
│ acks   │ Latency    │ Durability       │ Use case               │
├────────┼────────────┼──────────────────┼────────────────────────┤
│ 0      │ ⭐⭐⭐⭐⭐  │ ⚠️ None           │ Metrics, fire-and-forget│
│ 1      │ ⭐⭐⭐⭐    │ ✅ Good           │ General default         │
│ all    │ ⭐⭐       │ 🛡️ Strongest     │ Money, audit, critical  │
└────────┴────────────┴──────────────────┴────────────────────────┘
⚙️ Pairs Importantly With
🔹 min.insync.replicas — when acks=all, this defines how many replicas MUST be in sync. If fewer, producer fails (rather than silently writing to fewer copies).
🔹 retries — producer retries on failure (with idempotence enabled, no duplicates).
🔹 enable.idempotence=true — for exactly-once semantics, set this with acks=all.
CLOSING HOOK
"Acks is the durability dial. Crank it up for safety (acks=all + min.insync.replicas=2 + RF=3), or dial down for speed (acks=1). 'No silver bullet — pick based on what you can afford to lose.'"
🧠 Key Phrases to Drop
acks = durability dial acks=all + RF=3 + min.insync=2 → no data loss Throughput vs durability trade-off acks=all required for exactly-once
QUESTION 12
🔹 Message Delivery Semantics — at-most-once, at-least-once, exactly-once
💡 Quick Definition
Three guarantees Kafka can offer for message delivery:

🔹 At-most-once — message may be lost, but never duplicated
🔹 At-least-once — message never lost, but may be duplicated
🔹 Exactly-once — never lost, never duplicated (the holy grail)
✨ "How many times can a message be delivered?" — the fundamental distributed systems question.
📦 The Three Semantics
1 At-Most-Once (Fire & Forget)
Producer: acks=0, no retries.
Consumer: commit offset BEFORE processing (auto-commit).
✅ Highest throughput, simplest
❌ Messages can be lost on failure
🎯 Use for: metrics, telemetry, click streams where loss is OK
2 At-Least-Once (Default)
Producer: acks=all, retries enabled.
Consumer: process THEN commit offset.
✅ No data loss
❌ Possible duplicates (e.g., if consumer crashes between processing and commit)
🎯 Use for: most workloads — pair with idempotent consumers
3 Exactly-Once (EOS)
Producer: enable.idempotence=true + transactions.
Consumer: isolation.level=read_committed.
Use Kafka transactions for atomic write across topics + offset commit.
✅ No loss, no duplicates
❌ Slightly slower
🎯 Use for: financial transactions, billing, exactly-once processing pipelines
⚠️ Where Duplicates Actually Come From
🔹 Producer retries — message sent, ack lost, producer retries → broker has 2 copies
🔹 Consumer rebalances — partition reassigned mid-processing → next consumer reprocesses
🔹 Consumer crash — processed but didn't commit → next time reprocesses

Solutions: idempotent producer (no producer-side dupes), transactions (atomic write+commit), idempotent consumer (handle dupes gracefully).
CLOSING HOOK
"Default Kafka is at-least-once. Most real-world systems combine at-least-once delivery + idempotent consumers — simpler than full EOS, just as effective. 'Make consumers idempotent and duplicates don't hurt.'"
🧠 Key Phrases to Drop
At-most-once / at-least-once / exactly-once Idempotent producer for no dupes Transactions for atomic write+commit Idempotent consumer pattern
QUESTION 13
🔹 Idempotent Producer
💡 Quick Definition
An idempotent producer is one where retrying a message never causes duplicates. Kafka achieves this by tagging each batch with a unique producer ID and sequence number — the broker rejects duplicates automatically.
✨ Turn it on with one config — and never worry about duplicate writes from retries.
😱 The Problem It Solves
Without idempotence:
1️⃣ Producer sends message X to broker
2️⃣ Broker writes it
3️⃣ Broker's ack is lost on the network
4️⃣ Producer assumes failure, retries → message X stored TWICE

With idempotence: broker recognizes the retry by sequence number → discards duplicate.
🛠️ How to Enable
enable.idempotence    = true
acks                  = all      // auto-set when idempotence=true
retries               = Integer.MAX_VALUE
max.in.flight.requests.per.connection = 5  // auto-capped
From Kafka 3.0+, idempotence is enabled by default. Just don't disable it.
🔑 How It Works Internally
🔹 Producer gets a unique Producer ID (PID) from the broker on startup
🔹 Each message batch gets an incrementing sequence number per partition
🔹 Broker tracks the highest seq number it's seen per (PID, partition)
🔹 If broker sees a batch with a seq number ≤ already-stored, → discards it
🔹 If seq number is too far ahead → throws an error (gap detected)
⚠️ Important Notes
🔹 Idempotence is per producer session. If the producer restarts, it gets a new PID — duplicates across sessions still possible (need transactions for that).
🔹 Idempotence is per partition. Order is preserved per partition.
🔹 Has very minimal overhead — basically free.
CLOSING HOOK
"Idempotent producer = 'safe retries' for free. It prevents duplicates from network glitches at the producer level. 'If you're not using it, you're inviting bugs.'"
🧠 Key Phrases to Drop
Producer ID + sequence number Default since Kafka 3.0 Prevents retry-induced duplicates Per-session, per-partition guarantee
QUESTION 14
🔹 Kafka Transactions
💡 Quick Definition
Kafka transactions let a producer write to multiple topics/partitions atomically — and atomically commit consumer offsets at the same time. Either everything succeeds, or everything is rolled back. Foundation of exactly-once semantics for stream processing.
✨ "All-or-nothing" writes across multiple Kafka topics — like ACID for streams.
💸 Analogy: Imagine transferring $100 from account A to account B. You need BOTH writes (debit A, credit B) to either both succeed or both fail. That's a transaction. Kafka transactions do the same for messages across topics.
🎯 What Transactions Enable
1 Atomic Multi-Topic Writes
Write to orders and inventory topics — both succeed or both fail.
2 Read-Process-Write Atomicity
In Kafka Streams pipelines: read from input topic, transform, write to output topic, commit offset — all atomic.
3 Exactly-Once Semantics (EOS)
Combined with idempotent producer, you get true exactly-once processing.
🛠️ How to Use
// Producer config
transactional.id      = "my-app-tx-1"     // unique per producer instance
enable.idempotence    = true
acks                  = all

// Producer code
producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord("orders", ...));
    producer.send(new ProducerRecord("inventory", ...));
    producer.sendOffsetsToTransaction(offsets, consumerGroupId);
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}
📥 Consumer Side — read_committed
Consumers must set isolation.level = read_committed to only see committed transactional messages. Default is read_uncommitted (sees everything, even from aborted transactions).
⚠️ Performance Cost
🔹 ~10–25% throughput overhead vs non-transactional
🔹 Higher end-to-end latency
🔹 Use only when you really need atomicity / EOS
🔹 For simple at-least-once + idempotent consumers, transactions are overkill
CLOSING HOOK
"Kafka transactions = 'database-like atomicity for streams'. Power Kafka Streams' exactly-once mode and any 'read-process-write' pipeline needing strict guarantees. 'Powerful but expensive — use sparingly.'"
🧠 Key Phrases to Drop
Atomic multi-partition writes read_committed isolation Read-process-write atomicity Required for exactly-once processing
QUESTION 15
🔹 Retention Policies & Log Compaction
💡 Quick Definition
Kafka stores messages on disk — but not forever. Retention policies control when old messages are deleted. There are two main strategies:

🔹 Time/Size-based deletion — delete old messages after X hours or X bytes
🔹 Log compaction — keep only the latest message for each key (forever)
✨ Retention controls what stays. Deletion = "expire by age". Compaction = "keep only the latest per key".
⏱️ Time-Based Retention (default)
log.retention.hours      = 168       # 7 days (default)
log.retention.minutes    = (override)
log.retention.ms         = (most precise)
Old segments are deleted after the threshold. Most common policy.
💾 Size-Based Retention
log.retention.bytes      = 1073741824  # 1 GB per partition
Once partition exceeds the size, oldest segments deleted. Often combined with time-based (whichever fires first).
🗜️ Log Compaction (the magical one)
With log.cleanup.policy = compact, Kafka keeps only the latest message per key — older messages with the same key are removed.

Perfect for state snapshots: imagine a topic where each message is a user's current profile. You don't need history — only the latest.
🎯 Compaction Example
Original log:
  (user1, "name=Amit")
  (user2, "name=John")
  (user1, "name=Amit Rakhaiya")     ← newer
  (user3, "name=Maria")
  (user1, "name=Amit R.")           ← newest for user1

After compaction:
  (user2, "name=John")
  (user3, "name=Maria")
  (user1, "name=Amit R.")           ← only the latest
🌟 When to Use Each
📅 Time-based deletion
Logs, events, metrics — anything where older data loses value over time.
🗜️ Log compaction
User profiles, account balances, configuration changes — anything where you only care about the LATEST state per key.
🔀 Both (compact + delete)
Set cleanup.policy=compact,delete — keep latest per key, but also delete keys absent for X days.
🎯 Famous Use Case
Kafka's own __consumer_offsets topic uses log compaction — only the latest committed offset per (group, topic, partition) is kept.
CLOSING HOOK
"Retention controls history. Compaction controls state. Time-based deletion = "stream of events". Compaction = "table of latest values". Master both, and Kafka becomes both a queue AND a database."
🧠 Key Phrases to Drop
log.retention.hours cleanup.policy = delete or compact Latest value per key (compaction) Powers __consumer_offsets
QUESTION 16
🔹 Partition Assignment Strategies
💡 Quick Definition
When multiple consumers in a group subscribe to a topic, Kafka must decide which consumer gets which partition. That's the job of the partition assignment strategy (also called the "assignor").
✨ Different strategies = different ways of dividing partitions among consumers fairly.
📦 The 4 Strategies
1 RangeAssignor (default before 2.4)
For each topic: divides partitions into ranges, assigns one range per consumer.
Example: 6 partitions, 3 consumers → C1: P0-P1, C2: P2-P3, C3: P4-P5.
❌ Can be unbalanced if consumers subscribe to multiple topics with different partition counts.
2 RoundRobinAssignor
Distributes ALL partitions of ALL topics round-robin across consumers.
Example: P0→C1, P1→C2, P2→C3, P3→C1, ...
✅ Better balanced across topics.
❌ Causes large reassignments on rebalance.
3 StickyAssignor
Like RoundRobin, but tries to preserve previous assignments across rebalances.
✅ Minimizes partition movement → less disruption.
❌ Still uses stop-the-world rebalancing.
4 CooperativeStickyAssignor (modern, recommended)
Sticky + incremental rebalancing.
Only the consumers losing/gaining partitions pause briefly. Others keep working.
✅ Massive reduction in rebalance pain. Available since Kafka 2.4.
🎯 Default since Kafka 3.x for new applications.
🛠️ How to Configure
partition.assignment.strategy =
  org.apache.kafka.clients.consumer.CooperativeStickyAssignor
⚠️ Why It Matters
Bad assignment strategies → uneven load (some consumers idle, others overloaded). And every rebalance with non-cooperative strategies pauses the entire group, causing latency spikes. CooperativeStickyAssignor is the modern best practice.
CLOSING HOOK
"Use CooperativeStickyAssignor in modern setups — it's the only one that doesn't grind your consumers to a halt during rebalances. 'Rebalances should sting, not paralyze.'"
🧠 Key Phrases to Drop
Range / RoundRobin / Sticky / Cooperative Cooperative = incremental rebalancing Modern default since 3.x Minimize partition movement
QUESTION 17
🔹 Consumer Offset Management (auto vs manual commit)
💡 Quick Definition
Consumers must commit offsets so Kafka knows what they've read. There are two strategies:

🔹 Auto-commit — Kafka commits in the background periodically
🔹 Manual commit — your code calls commitSync() or commitAsync() explicitly
✨ Auto-commit = simple but lossy/duplicaty. Manual commit = correct but you do the bookkeeping.
⚙️ Auto-Commit (default)
enable.auto.commit       = true
auto.commit.interval.ms  = 5000     # every 5 sec
🔹 ✅ Simple — no code needed
🔹 ❌ Risky for at-least-once: commit happens BEFORE message is fully processed
🔹 ❌ Crashes between commits → unprocessed messages "lost"
🎯 OK for prototypes; risky for production
🔧 Manual Commit (recommended)
enable.auto.commit = false

while (running) {
    ConsumerRecords records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord r : records) {
        process(r);
    }
    consumer.commitSync();    // commit AFTER processing
}
🚦 Two Manual Commit Modes
1 commitSync()
Blocks until broker acknowledges. Safe, but slower. Best for batch processing where correctness > throughput.
2 commitAsync()
Fires and forgets (with optional callback). Faster, but if it fails silently, may leave offsets uncommitted.
⭐ Common pattern
Use commitAsync() in the poll loop, but call commitSync() on shutdown to flush.
📊 Comparison
┌──────────────────┬───────────────────┬────────────────────┐
│ Strategy         │ Risk              │ Use case           │
├──────────────────┼───────────────────┼────────────────────┤
│ auto-commit      │ Possible loss/dup │ Prototyping        │
│ commitSync       │ None (but slower) │ Critical workloads │
│ commitAsync      │ Silent failure    │ High throughput    │
│ async + sync     │ Best balance      │ Production default │
└──────────────────┴───────────────────┴────────────────────┘
CLOSING HOOK
"Process FIRST, commit AFTER — that's the at-least-once mantra. Auto-commit reverses it (commit before fully processing) → lost messages on crash. 'Manual commit = correctness in your hands.'"
🧠 Key Phrases to Drop
enable.auto.commit = false in production commitSync vs commitAsync Process then commit Async in loop, sync on shutdown
QUESTION 18
🔹 Consumer Rebalancing
💡 Quick Definition
Rebalancing is the process by which Kafka redistributes partitions among consumers in a group when membership changes. It happens when:

🔹 A consumer joins or leaves the group
🔹 A consumer crashes / heartbeat times out
🔹 New partitions are added to a subscribed topic
🔹 Subscribed topics list changes
✨ "Reshuffle the deck so each player gets a fair hand" — but during reshuffle, no one plays.
⚠️ The Problem with Classic Rebalancing
Default behavior is "stop-the-world":
1️⃣ All consumers stop processing
2️⃣ They give up all partitions
3️⃣ Group leader recomputes assignments
4️⃣ Each consumer gets new partitions
5️⃣ Processing resumes

Even brief rebalances cause latency spikes & lag bumps. With many consumers, can take 30+ seconds!
⚡ Cooperative Rebalancing (Modern Fix)
Available since Kafka 2.4 (KIP-429). With CooperativeStickyAssignor:
🔹 Only consumers losing or gaining partitions pause briefly
🔹 The rest keep processing uninterrupted
🔹 Rebalance happens in incremental phases
🔹 Massive reduction in rebalance impact
⚙️ Important Configurations
session.timeout.ms        = 45000  # consumer dies if no heartbeat
heartbeat.interval.ms     = 3000   # heartbeat frequency
max.poll.interval.ms      = 300000 # max time between polls
partition.assignment.strategy = CooperativeStickyAssignor
🚨 Common Causes of Rebalances
1 Long Processing
Consumer takes longer than max.poll.interval.ms to process a batch → kicked out of group.
2 Network Issues
Consumer can't send heartbeats → broker assumes it's dead.
3 Garbage Collection
Long GC pauses block heartbeats → false eviction.
4 Scale Up/Down
Adding/removing consumer instances triggers rebalance.
🛡️ How to Minimize Pain
🔹 Use CooperativeStickyAssignor
🔹 Use static membership (group.instance.id) for K8s — survives rolling restarts
🔹 Tune max.poll.records to keep processing time short
🔹 Increase max.poll.interval.ms if processing is genuinely slow
🔹 Avoid long GC pauses — tune JVM
CLOSING HOOK
"Rebalances are unavoidable but tameable. Use cooperative rebalancing + static membership + reasonable poll intervals — and your consumers stay smooth even during deployments. 'A bad rebalance can spike lag by minutes.'"
🧠 Key Phrases to Drop
Stop-the-world rebalance CooperativeStickyAssignor (KIP-429) Static membership for stable IDs max.poll.interval.ms timeout

🔹 What is Kafka Connect?
💡 Quick Definition
Kafka Connect is a framework for moving data between Kafka and external systems (databases, file systems, cloud storage, search engines, etc.) — without writing custom integration code.
✨ "Plug-and-play data integration for Kafka." — declarative, scalable, no custom producers/consumers.
🔌 Analogy: Kafka Connect is like a universal power adapter. Instead of writing a custom plug for every appliance (database / S3 / Elasticsearch), you use a pre-built adapter ("connector"). Configure it via JSON, plug it in, data flows.
🔄 Two Types of Connectors
1 Source Connector (Data → Kafka)
Pulls data FROM external systems INTO Kafka. Examples: Debezium (MySQL/Postgres CDC), JDBC Source, MongoDB Source, FilePulse.
2 Sink Connector (Kafka → Data)
Pushes data FROM Kafka TO external systems. Examples: Elasticsearch Sink, S3 Sink, JDBC Sink, BigQuery Sink, MongoDB Sink.
🎯 Famous Use Case — Debezium for CDC
Change Data Capture (CDC): Debezium reads MySQL/Postgres binlogs and publishes every INSERT/UPDATE/DELETE as Kafka events.

Result: your database becomes a real-time event source. Other services subscribe to changes — no polling, no triggers, no batch ETL.
🛠️ Configuration Example
{
  "name": "jdbc-source-orders",
  "config": {
    "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
    "connection.url": "jdbc:mysql://db:3306/shop",
    "table.whitelist": "orders",
    "topic.prefix": "db-",
    "mode": "incrementing",
    "incrementing.column.name": "id"
  }
}
🌟 Why Use It?
🔹 No custom producers/consumers — just config
🔹 Distributed mode — runs as a cluster, scales horizontally, fault-tolerant
🔹 Hundreds of connectors available (Confluent Hub)
🔹 Exactly-once support in many connectors
🔹 Schema integration via Schema Registry
CLOSING HOOK
"Kafka Connect = 'integration without code'. Config-driven, scalable, exactly-once. Combined with Debezium, your databases become first-class event sources. 'Stop writing one-off pipelines — declare them.'"
🧠 Key Phrases to Drop
Source vs Sink connectors Debezium for CDC Distributed mode (HA cluster) Config-driven, no code
QUESTION 20
🔹 What is Kafka Streams?
💡 Quick Definition
Kafka Streams is a Java library for building stream-processing applications on top of Kafka. You read from Kafka topics, transform/aggregate the data, and write the results back to Kafka — all within your normal Java app, no separate cluster needed.
✨ Stream processing as a library — not a separate cluster like Spark or Flink.
🌟 What Makes It Different
Unlike Apache Spark Streaming or Flink (which run as separate clusters), Kafka Streams is just a JAR you embed in your Java app. No new infrastructure to deploy.

🔹 Just a Spring Boot app + Kafka Streams = stream-processing service
🔹 Scales by running more instances (uses Kafka consumer groups under the hood)
🔹 Stateful processing with built-in state stores (RocksDB)
🛠️ Simple Example
StreamsBuilder builder = new StreamsBuilder();

builder.stream("orders")
       .filter((k, v) -> v.getAmount() > 100)
       .mapValues(order -> enrich(order))
       .to("big-orders");

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();
🎯 Capabilities
1 Filter / Map / FlatMap
Stateless transformations on streams.
2 GroupBy + Aggregate
Stateful aggregation: count, sum, average per key. Backed by local state store.
3 Windowing
Tumbling, hopping, session windows — "count events per 5-minute window".
4 Joins
Stream-Stream, Stream-Table, Table-Table joins (for enrichment).
5 Exactly-Once Semantics
Built-in EOS via Kafka transactions — read-process-write atomically.
6 Interactive Queries
Query state stores from your app — turn streams into queryable views.
📊 Stream vs Table (Duality)
Kafka Streams treats data as either:
🔹 KStream — append-only stream of events (e.g., page views)
🔹 KTable — current state per key (e.g., user count per region) — backed by compacted topic

These are dual — a stream can be aggregated into a table, a table can be turned into a stream of changes (CDC).
⚖️ When to Use Kafka Streams vs Spark/Flink
🔹 Kafka Streams — when your stream processing fits within microservices. Lightweight, no extra cluster.
🔹 Flink/Spark — for complex pipelines, ML integration, batch+stream unification, or when teams already use them.
CLOSING HOOK
"Kafka Streams = 'stream processing without the infrastructure tax'. It turns any Java service into a real-time data processor with a few lines of code. 'If your data lives in Kafka, process it in Kafka.'"
🧠 Key Phrases to Drop
Library, not a cluster KStream and KTable duality Built-in exactly-once RocksDB-backed state stores
QUESTION 21
🔹 Schema Registry & Avro
💡 Quick Definition
Kafka stores raw bytes — it doesn't care about schema. But producers and consumers must agree on the format. Schema Registry is a centralized service that stores and versions schemas (Avro, Protobuf, JSON Schema) — ensuring producers and consumers stay compatible as schemas evolve.
✨ "Contract management for Kafka data" — schemas as a service.
😱 The Problem It Solves
Without Schema Registry:
🔹 Producer adds a new field → consumer crashes parsing JSON
🔹 No central place to know "what's the format of orders topic?"
🔹 Schema documentation drifts out of sync

With Schema Registry:
🔹 Producer registers schema (with version)
🔹 Consumer fetches schema by ID — knows exactly how to decode
🔹 Compatibility rules prevent breaking changes
🛠️ How It Works
1️⃣ Producer serializes message with schema → registers schema with registry → gets schema ID
2️⃣ Producer prepends schema ID to message payload (5 bytes)
3️⃣ Sends to Kafka
4️⃣ Consumer receives message → reads schema ID → fetches schema from registry → deserializes
📦 Avro — The Most Popular Format
Apache Avro = compact binary format with schema. Schema describes fields, types, defaults.
🔹 ✅ Compact (smaller than JSON)
🔹 ✅ Schema evolution rules built-in
🔹 ✅ Code generation possible
🔹 ❌ Not human-readable
🛡️ Schema Compatibility Modes
1 BACKWARD (most common)
New schema can read old data. Allows: adding optional fields, removing fields. Deploy consumers first.
2 FORWARD
Old schema can read new data. Deploy producers first.
3 FULL
Both backward AND forward compatible. Strongest guarantee.
4 NONE
No compatibility check. Use at your own risk.
🛠️ Tools
🔹 Confluent Schema Registry — most popular, free for development
🔹 Apicurio — open-source alternative
🔹 AWS Glue Schema Registry — managed cloud

Supported formats: Avro, Protobuf, JSON Schema
CLOSING HOOK
"Schema Registry = 'API contracts for events'. Without it, schema changes break your consumers silently. 'Treat your event schemas like REST API contracts — versioned, documented, validated.'"
🧠 Key Phrases to Drop
Centralized schema management Avro / Protobuf / JSON Schema BACKWARD / FORWARD / FULL compatibility Schema ID in message header
QUESTION 22
🔹 Why is Kafka so fast?
💡 Purpose
Kafka achieves millions of messages per second on commodity hardware — sometimes faster than in-memory systems. This isn't magic — it's a combination of clever design choices that exploit modern hardware and OS features.
✨ Kafka cheats — it lets the OS do the heavy lifting.
⚡ The 6 Reasons Kafka is Fast
1 Sequential Disk I/O
Kafka writes to disk sequentially (append-only log). Sequential disk writes can be as fast as RAM — much faster than random writes. Hardware-friendly.
2 Zero-Copy via sendfile()
When sending data to consumers, Kafka uses Linux's sendfile() system call. Data goes directly from disk to network socket — without copying to user space. Saves CPU and time.
3 OS Page Cache
Kafka relies on OS page cache instead of managing its own. Reads usually hit memory. Restarting Kafka doesn't lose the cache — only the OS knows.
4 Producer Batching
Producer accumulates messages in memory (batch.size, linger.ms) and sends them as one big batch — fewer network calls, more data per call.
5 Compression
Compresses entire batches (gzip, snappy, lz4, zstd). Less network bandwidth, less disk space — usually a 2-10x reduction.
6 Partitioning + Parallelism
Partitions are independent. Multiple producers, multiple consumers, multiple brokers — all in parallel. Linear horizontal scaling.
🚀 Bonus Perf Tricks
🔹 Pull-based consumers — consumers control rate, no broker buffering
🔹 Binary protocol — efficient wire format
🔹 No message indexing — just sequential offsets, O(1) lookup
🔹 Asynchronous replication with batching
CLOSING HOOK
"Kafka's speed comes from embracing the disk + leveraging the OS + batching everything. It treats memory as a cache, the disk as primary storage, and the network as a stream of batches. 'Sequential I/O + zero-copy + batching = millions of msg/sec.'"
🧠 Key Phrases to Drop
Sequential disk I/O Zero-copy (sendfile) OS page cache Batching + compression Append-only log

🔹 Important Producer & Consumer Configurations
💡 Purpose
Kafka has 100+ config options. You don't need them all — but you MUST know the dozen that matter most for production. Interviewers ask about these constantly.
📤 Producer Configurations
1 bootstrap.servers
Comma-separated list of brokers to connect to. broker1:9092,broker2:9092
2 acks
0 / 1 / all — durability vs speed trade-off. Default: 1 (or "all" if idempotence enabled).

How many times to retry on failure. With idempotence on, set to Integer.MAX_VALUE.
4 batch.size
Max bytes per batch (default 16 KB). Larger = more throughput, more latency.

How long to wait for batch to fill (default 0). Increase to ~5-10ms for better batching.
6 compression.type
none / gzip / snappy / lz4 / zstd. lz4 or zstd = best balance.
7 enable.idempotence
true → no duplicates from retries. Default true since Kafka 3.0.
8 key.serializer / value.serializer
How to serialize key/value (StringSerializer, AvroSerializer, etc.).

1 bootstrap.servers
Same as producer.
2 group.id
Consumer group identifier. Determines work-sharing.
3 auto.offset.reset
earliest / latest / none — what to do if no committed offset.
4 enable.auto.commit
true / false. Set false in production for manual offset commits.
5 max.poll.records
Max records returned per poll() call (default 500). Tune to fit your processing time.
6 max.poll.interval.ms
Max time between polls before consumer is considered dead (default 5 min).
7 session.timeout.ms
How long without heartbeats before broker evicts consumer (default 45s).
8 fetch.min.bytes / fetch.max.wait.ms
Tune fetch batching — wait for more bytes or up to N ms.
9 isolation.level
read_uncommitted (default) or read_committed (only see committed transactional messages).

retries=2147483647
linger.ms=10
compression.type=lz4
batch.size=32768

# Consumer

auto.offset.reset=earliest
max.poll.records=500
isolation.level=read_committed
partition.assignment.strategy=CooperativeStickyAssignor

🔹 Kafka Security & Monitoring
💡 Purpose
In production, Kafka must be secure (auth, encryption, ACLs) and observable (lag, throughput, errors). Both come up frequently in senior interviews.
✨ Security: who can connect, what they can do. Monitoring: is everything healthy?
🛡️ Security — The 4 Pillars
1 Encryption in Transit (SSL/TLS)
Encrypts traffic between producers, consumers, and brokers. Prevents eavesdropping. Configured via security.protocol=SSL.
2 Authentication (SASL)
Verifies who the client is. Mechanisms:
🔹 SASL/PLAIN (username + password)
🔹 SASL/SCRAM (salted, hashed passwords)
🔹 SASL/GSSAPI (Kerberos for enterprise)
🔹 SASL/OAUTHBEARER (modern OAuth2)
3 Authorization (ACLs)
Controls what authenticated users can do. Per-topic, per-action: read, write, create, delete. Managed via kafka-acls.sh or Confluent RBAC.
4 Encryption at Rest
Disk-level encryption (LUKS, KMS, cloud volumes). Kafka itself doesn't encrypt data on disk natively — rely on infra.
📊 Monitoring — What to Watch
1 Consumer Lag (most critical metric)
Difference between latest offset and committed offset. High lag = consumer can't keep up. Tools: Burrow, Kafka Lag Exporter, Confluent Control Center.
2 Throughput (bytes/sec, msg/sec)
Per-broker, per-topic. Identifies hot spots and capacity issues.
3 Broker Health
CPU, memory, disk, network. Disk usage especially — hitting full = brokers fail.
4 Under-Replicated Partitions
Partitions where some replicas are out of sync. Should be 0 in healthy cluster.
5 Producer/Consumer Errors
Failed sends, timeouts, retry counts. Spikes = something's wrong.
6 Request Latency
p50/p99 latencies for produce and fetch requests. SLA visibility.
