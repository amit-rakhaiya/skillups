Q 01
Local Variable Type Inference — var
Java Java10+

var lets the compiler infer the type of a local variable — reduces boilerplate without losing static typing.

Before vs After
// Before Java 10
Map<String, List<Person>> personMap = new HashMap<String, List<Person>>();

// With var — compiler infers the type
var personMap = new HashMap<String, List<Person>>();
var list = new ArrayList<String>();
var name = "Amit";   // inferred as String
Rules
✅ Allowed❌ Not Allowed
Local variables with initializerMethod parameters
for / enhanced-for loop variablesReturn types
try-with-resources variablesClass fields
Lambda parameters (Java 11)var x; — no initializer
// Java 11 — var in lambda parameters (enables annotations)
var list = List.of("a", "b", "c");
list.forEach((@NotNull var item) -> System.out.println(item));
💡 Key point: var is still statically typed — type is resolved at compile time, not runtime. It is NOT like JavaScript's var. Avoid using it when the type is not obvious from the right-hand side — hurts readability.

Q 03
HTTP Client API
Java Java11

Java 11 standardized the HTTP Client (was incubating in Java 9/10). Supports HTTP/1.1, HTTP/2, WebSocket, sync & async calls.

Synchronous GET
HttpClient client = HttpClient.newHttpClient();

HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://api.example.com/users"))
    .header("Accept", "application/json")
    .GET()
    .build();

HttpResponse<String> response = client.send(request,
    HttpResponse.BodyHandlers.ofString());

System.out.println(response.statusCode()); // 200
System.out.println(response.body());
Asynchronous POST
HttpClient client = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_2)
    .connectTimeout(Duration.ofSeconds(10))
    .build();

HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://api.example.com/users"))
    .header("Content-Type", "application/json")
    .POST(HttpRequest.BodyPublishers.ofString("{\"name\":\"Amit\"}"))
    .build();

// Non-blocking
client.sendAsync(request, HttpResponse.BodyHandlers.ofString())
    .thenApply(HttpResponse::body)
    .thenAccept(System.out::println)
    .join();
💡 vs RestTemplate/WebClient: Java's built-in HTTP Client is lightweight with no dependencies. In Spring apps, WebClient (reactive) or RestTemplate are preferred. Built-in client is useful for non-Spring modules or utilities.
Q 04
Switch Expressions
Java Java14

Switch Expressions (preview Java 12, standard Java 14) make switch return a value and eliminate fall-through bugs.

Old Switch Statement vs New Switch Expression
// Old — verbose, fall-through risk, no value
String result;
switch (day) {
    case MONDAY:
    case TUESDAY:
        result = "Weekday";
        break;
    case SATURDAY:
    case SUNDAY:
        result = "Weekend";
        break;
    default:
        result = "Unknown";
}

// New Switch Expression — arrow syntax, returns value
String result = switch (day) {
    case MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY -> "Weekday";
    case SATURDAY, SUNDAY -> "Weekend";
};
yield — for multi-line blocks
int score = switch (grade) {
    case "A" -> 100;
    case "B" -> 80;
    case "C" -> {
        System.out.println("Average grade");
        yield 60;   // yield returns value from block
    }
    default -> 0;
};
Old SwitchNew Switch Expression
Returns value❌ No✅ Yes
Fall-through⚠️ Yes (bug-prone)❌ No (arrow syntax)
ExhaustivenessNot checkedCompiler enforces all cases
Multi-casecase A: case B:case A, B ->
💡 Key: Use yield only inside block cases { }. Arrow cases -> return directly without yield.

Text Blocks
Java Java15

Text blocks (preview Java 13, standard Java 15) allow multi-line string literals without escape sequences.

// Before — ugly escape sequences
String json = "{\n" +
              "  \"name\": \"Amit\",\n" +
              "  \"role\": \"Architect\"\n" +
              "}";

// Text Block
String json = """
        {
          "name": "Amit",
          "role": "Architect"
        }
        """;
Real-world Use Cases
// SQL
String sql = """
        SELECT u.name, u.email
        FROM users u
        WHERE u.active = true
        ORDER BY u.name
        """;

// HTML template
String html = """
        <div class="card">
            <h2>%s</h2>
            <p>%s</p>
        </div>
        """.formatted(title, description);
Indentation Rules
// Closing """ controls indentation
String s = """
        line1
        line2
        """;   // trailing newline included, common indent stripped

// No trailing newline — place closing """ on last line
String s = """
        line1
        line2""";
💡 Key: The position of the closing """ determines the common indent that gets stripped. Text blocks also support \ (line continuation) and \s (explicit trailing space).

Records
Java Java16

Records are immutable data carriers — the compiler auto-generates constructor, getters, equals(), hashCode(), and toString().

Before vs After
// Before — 40+ lines of boilerplate
public final class Person {
    private final String name;
    private final int age;
    public Person(String name, int age) { this.name = name; this.age = age; }
    public String name() { return name; }
    public int age() { return age; }
    @Override public boolean equals(Object o) { ... }
    @Override public int hashCode() { ... }
    @Override public String toString() { ... }
}

// Record — 1 line
public record Person(String name, int age) {}
What's auto-generated
Person p = new Person("Amit", 35);
p.name()         // accessor (not getName())
p.age()          // accessor
p.equals(other)  // deep equality on all components
p.hashCode()     // based on all components
p.toString()     // "Person[name=Amit, age=35]"
Custom compact constructor — validation
public record Person(String name, int age) {
    // Compact constructor — no parameter list needed
    Person {
        if (age < 0) throw new IllegalArgumentException("Age cannot be negative");
        name = name.trim(); // can transform parameters
    }
}
What Records CANNOT do
RestrictionReason
Cannot extend another classImplicitly extends Record
Cannot have mutable fieldsAll components are final
Cannot be abstractRecords are implicitly final
Cannot add instance fieldsOnly declared components allowed
💡 Use case: DTOs, API response/request objects, value objects in DDD. In our Camunda POC we use record Person(...) as DTO — replaces a Lombok @Data class with zero boilerplate and true immutability.
Q 07
Pattern Matching — instanceof
Java Java16

Eliminates the verbose cast-after-instanceof pattern.

// Before Java 16 — check then cast (redundant)
if (obj instanceof String) {
    String s = (String) obj;   // redundant cast
    System.out.println(s.length());
}

// Java 16+ — bind variable in the pattern
if (obj instanceof String s) {
    System.out.println(s.length());  // s is already String, scoped to if block
}

// With condition
if (obj instanceof String s && s.length() > 5) {
    System.out.println("Long string: " + s);
}
Real-world — polymorphic processing
double calculate(Object shape) {
    if (shape instanceof Circle c) {
        return Math.PI * c.radius() * c.radius();
    } else if (shape instanceof Rectangle r) {
        return r.width() * r.height();
    } else if (shape instanceof Triangle t) {
        return 0.5 * t.base() * t.height();
    }
    throw new IllegalArgumentException("Unknown shape");
}
💡 Scope: The bound variable (s, c) is scoped to the block where the pattern matches — not available in the else branch. Java 21 extends this to switch expressions (see Q11).
Q 08
Sealed Classes
Java Java17

Sealed classes restrict which classes can extend or implement them — gives you a closed type hierarchy that the compiler can reason about exhaustively.

// Sealed class — only permitted subtypes can extend
public sealed class Shape permits Circle, Rectangle, Triangle {}

public final class Circle    extends Shape { double radius; }
public final class Rectangle extends Shape { double width, height; }
public non-sealed class Triangle extends Shape { }  // open again
Three permitted modifiers on subclass
ModifierMeaning
finalCannot be extended further
sealedFurther restricted — must declare its own permits
non-sealedOpens the hierarchy back up — anyone can extend
Why Sealed Classes? — Exhaustive pattern matching
// Compiler knows ALL possible subtypes → enforces exhaustiveness
double area = switch (shape) {
    case Circle c    -> Math.PI * c.radius() * c.radius();
    case Rectangle r -> r.width() * r.height();
    case Triangle t  -> 0.5 * t.base() * t.height();
    // No default needed — compiler verifies all cases covered
};
Real-world Use Cases
  • 💰
    Payment types: sealed interface Payment permits CreditCard, BankTransfer, Crypto
  • 📨
    API responses: sealed interface Result permits Success, Failure, Pending
  • 🔄
    State machines: model fixed set of states with compile-time exhaustiveness
💡 Key relationship: Sealed classes + Pattern matching switch + Records = Java's answer to algebraic data types (like Scala case classes or Kotlin sealed classes). Together they enable safe, exhaustive domain modeling.
Q 09
Virtual Threads — Project Loom
Java Java21 Concurrency

Virtual threads are lightweight threads managed by the JVM (not OS). Millions can run concurrently — solving the thread-per-request scalability problem without reactive programming.

Platform Thread vs Virtual Thread
Platform Thread (old): Java Thread → OS Thread (1:1 mapping) Stack: ~1MB per thread Context switch: expensive (OS kernel) Practical limit: ~thousands Virtual Thread (Java 21): Java VThread → Carrier Thread (M:N mapping) Stack: tiny (grows dynamically, starts at ~KB) Context switch: JVM-managed (cheap) Practical limit: millions
Creating Virtual Threads
// 1. Direct creation
Thread vt = Thread.ofVirtual().start(() -> System.out.println("Hello"));

// 2. Via executor (recommended for server apps)
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1)); // blocks without wasting OS thread
            return "done";
        });
    }
}

// 3. Spring Boot 3.2+ — enable with one property
spring.threads.virtual.enabled=true
Key Behaviour — Blocking is OK
// With platform threads — blocking wastes OS thread
// With virtual threads — JVM unmounts virtual thread from carrier,
// carrier thread is free to run other virtual threads

// This is fine with virtual threads:
String result = httpClient.send(request, bodyHandler).body(); // blocking I/O
Files.readString(path);  // blocking file I/O
Thread.sleep(1000);      // blocking sleep
When to Use
Good fit ✅Not a fit ❌
High-concurrency I/O-bound work (REST, DB calls)CPU-intensive computation
Thread-per-request server modelAlready reactive (WebFlux)
Replacing thread pool with simple blocking codePinning (synchronized blocks hold carrier)
💡 Spring Boot 3.2+: Set spring.threads.virtual.enabled=true — all request handling moves to virtual threads instantly. This is the main reason to upgrade to Java 21 for server-side apps.

Sequenced Collections
Java Java21 Collections

Java 21 added three new interfaces to give a uniform API for collections that have a defined encounter order.

SequencedCollection extends Collection ├── addFirst(e), addLast(e) ├── getFirst(), getLast() ├── removeFirst(), removeLast() └── reversed() ← returns reversed view SequencedMap extends Map ├── firstEntry(), lastEntry() ├── putFirst(k,v), putLast(k,v) └── sequencedKeySet(), sequencedValues()
// Before Java 21 — no uniform way to get first/last
list.get(0);                          // List
deque.peekFirst();                    // Deque
linkedHashMap.entrySet().iterator().next(); // LinkedHashMap

// Java 21 — uniform API
list.getFirst();
deque.getFirst();
linkedHashMap.firstEntry();
💡 Why it matters: Before Java 21, there was no common interface for "ordered collections with defined first/last". Different types had different methods. Sequenced Collections fixes this inconsistency.
Q 11
Pattern Matching for Switch
Java Java21

Extends switch to match on types, not just values. Combined with sealed classes for exhaustive, null-safe dispatch.

// Java 21 — type patterns in switch
static String describe(Object obj) {
    return switch (obj) {
        case Integer i  -> "Integer: " + i;
        case String s   -> "String of length " + s.length();
        case null       -> "null value";
        default         -> "Other: " + obj.getClass().getName();
    };
}

// Guarded patterns — add conditions with 'when'
static String classify(Object obj) {
    return switch (obj) {
        case Integer i when i > 0  -> "Positive integer";
        case Integer i when i < 0  -> "Negative integer";
        case Integer i             -> "Zero";
        case String s  when s.isBlank() -> "Blank string";
        case String s               -> "String: " + s;
        default                     -> "Other";
    };
}
With Sealed Classes — no default needed
sealed interface Shape permits Circle, Rectangle {}
record Circle(double r) implements Shape {}
record Rectangle(double w, double h) implements Shape {}

double area(Shape s) {
    return switch (s) {
        case Circle c    -> Math.PI * c.r() * c.r();
        case Rectangle r -> r.w() * r.h();
        // No default — compiler verifies exhaustiveness
    };
}
💡 Evolution: Java 16 added pattern matching to instanceof. Java 21 brings it to switch — enabling concise, type-safe, exhaustive dispatch. This is the culmination of the Amber project.
Q 12
Optional API — Best Practices
Java

Optional<T> is a container that may or may not hold a value — designed to eliminate NullPointerExceptions in return types.

// Creating
Optional<String> opt = Optional.of("Amit");       // throws NPE if null
Optional<String> opt = Optional.ofNullable(name); // safe — wraps null
Optional<String> opt = Optional.empty();

// Extracting
opt.get()                  // throws NoSuchElementException if empty — avoid!
opt.orElse("default")      // return default if empty
opt.orElseGet(() -> compute()) // lazy default — only computed if empty
opt.orElseThrow()          // throws NoSuchElementException (Java 10+)
opt.orElseThrow(CustomEx::new)

// Transforming
opt.map(String::toUpperCase)          // transform if present
opt.flatMap(s -> findByName(s))       // for methods returning Optional
opt.filter(s -> s.length() > 3)       // filter on condition

// Java 11
opt.isEmpty()   // opposite of isPresent()
Do's and Don'ts
✅ Do❌ Don't
Use as return type of methodsUse as method parameter
Use orElse / orElseGet / orElseThrowUse get() without isPresent() check
Chain with map/flatMap/filterUse Optional as class field
Use in stream pipelineUse Optional<Collection> — return empty collection instead
💡 orElse vs orElseGet: orElse(createDefault()) — createDefault() is ALWAYS called even if value is present. orElseGet(() -> createDefault()) — only called if empty. Use orElseGet for expensive operations.

Q 14
What is a Stream and what easiness does it provide over conventional loops?
Java Collections

A Stream is a pipeline for processing sequences of elements — describes what to do, not how to iterate. Does not store data; processes it on demand.

Data Source → [ filter → map → sorted ] → Result Stream Pipeline (lazy — nothing runs until terminal op)
Same Problem — Loop vs Stream

Get names of active employees earning > 50000, sorted alphabetically.

// Conventional loop
List<String> result = new ArrayList<>();
for (Employee emp : employees) {
    if (emp.isActive() && emp.getSalary() > 50000) {
        result.add(emp.getName());
    }
}
Collections.sort(result);

// Stream
List<String> result = employees.stream()
    .filter(Employee::isActive)
    .filter(emp -> emp.getSalary() > 50000)
    .map(Employee::getName)
    .sorted()
    .toList();
What Easiness Streams Provide
1. Readability — Declarative (WHAT, not HOW)
// Loop — describes HOW (init, condition, increment, temp list)
for (int i = 0; i < list.size(); i++) {
    if (list.get(i) > 10) result.add(list.get(i) * 2);
}

// Stream — describes WHAT
list.stream().filter(n -> n > 10).map(n -> n * 2).toList();
2. Parallelism — One Word Change
employees.stream().filter(...).map(...).toList();       // sequential
employees.parallelStream().filter(...).map(...).toList(); // parallel — splits across CPU cores
// With loops: need ExecutorService, thread mgmt, result merging
3. Lazy Evaluation — Stops When Possible
// Does NOT process all 1 million elements — stops at first match
Optional<Employee> found = employees.stream()
    .filter(emp -> emp.getSalary() > 100000)
    .findFirst();  // short-circuits automatically
4. Built-in Aggregation — No Manual Loops
// Sum, average
int total = employees.stream().mapToInt(Employee::getSalary).sum();
OptionalDouble avg = employees.stream().mapToDouble(Employee::getSalary).average();

// Group by department
Map<String, List<Employee>> byDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment));

// Count per department
Map<String, Long> countByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment, Collectors.counting()));
Stream Pipeline Structure
Source Intermediate (lazy) Terminal (triggers execution) ────────── ────────────────────────── ───────────────────────── list.stream() → filter() → map() → sorted() → collect() / toList() / count() forEach() / findFirst() / reduce()
When to Use Loop vs Stream
Use LoopUse Stream
Need to modify external statePure transformation / aggregation
Complex multi-step logic with stateFilter / map / collect pipelines
Need element indexDeclarative data processing
Checked exceptions inside loopParallel processing needed
Performance-critical tight loopsReadability is priority
💡 One-liner: Streams provide a declarative, composable pipeline — eliminating boilerplate iteration, enabling lazy evaluation, and making parallelism trivial. Trade-off: debugging is harder and stateful logic is awkward inside stream operations.
Q 15
Why do we need Wrapper classes in Java?
Java Collections

Wrapper classes (Integer, Long, Boolean, etc.) encapsulate Java's primitive data types (int, long, boolean) into objects, bridging the gap between high-performance primitive processing and Java's object-oriented ecosystem.

🚀 Core Architectural Requirements
  • ⚙️
    Generics & Collections Framework: Java's Generics apply type erasure at compile-time and strictly require Object references. You cannot instantiate a List<int>; it must be a List<Integer>.
  • 🚫
    Nullability (APIs & Persistence): A primitive int defaults to 0, whereas an Integer wrapper defaults to null. In database entities (JPA/Hibernate) or REST API JSON payloads, differentiating between a value being explicitly zero versus completely unprovided is critical. Wrappers handle this naturally.
  • 🛠️
    Utility & Constants: They house crucial type-specific parsing, formatting, and mathematical utility methods (e.g., Integer.parseInt(), Double.isNaN()) along with structural boundaries like Integer.MAX_VALUE.
🧠 Senior Insight — The Memory & Cache Trap
The Performance Trade-off: Wrapper objects impose a heavy memory footprint. A primitive int takes exactly 4 bytes. An Integer object demands 16 bytes for the object header plus 4 bytes for the int payload, which gets padded to 24 bytes under 8-byte alignment—a massive layout expansion.

To alleviate this overhead, Java pools small integers via the Integer Cache (ranging from -128 to 127). This leads to a classic senior interview trap involving identity checks: 
Integer a = 100; Integer b = 100;
System.out.println(a == b); // true (Both pull from the pooled cache instance)

Integer x = 200; Integer y = 200;
System.out.println(x == y); // false (Values exceed 127; new distinct objects are allocated)
💡 Rule of Thumb: Primitives should be heavily favored in high-throughput math blocks, loops, or local temporary streams to avoid garbage collection pressure from heavy auto-boxing. Use wrappers strategically for data layers, entities, and collections.
Q 16
What is Autoboxing and Unboxing?
Java Collections

Autoboxing is the automatic conversion that the Java compiler performs between primitive types and their corresponding object wrapper classes. Unboxing is the exact reverse process. While clean syntactically, it can inject severe implicit execution overhead.

⚙️ Under-the-Hood Generation
// Code as written by the developer
List<Integer> list = new ArrayList<>();
list.add(10);             // Implicit Autoboxing
int num = list.get(0);    // Implicit Unboxing

// Code generated by the compiler after compilation
list.add(Integer.valueOf(10));
int num = list.get(0).intValue();
⚠️ Micro-Architectural Traps
  • ⏳
    Garbage Collection Pressure: Performing math operations or accumulations using wrapper accumulators within a tight loop forces massive object allocations behind the scenes. Declaring Long sum = 0L; inside a loop iterating 1 million times instantiates 1 million distinct Long garbage objects. Always use primitive accumulators.
  • 💥
    Implicit NullPointerExceptions: Attempting to assign a wrapper variable holding a null reference directly to a primitive variable triggers implicit unboxing (e.g., calling .intValue()), resulting in an immediate runtime crash.
Q 17
Are all Strings immutable?
Java

Yes, in Java, all instances of the java.lang.String class are strictly immutable. Once a string object lands on the heap, its character content cannot be structurally altered. Any mutation attempt triggers the transparent allocation of a new instance.

🛡️ Strategic Architectural Drivers
  • 💾
    The String Pool: To optimize memory layout, Java caches string literals. Multiple variables assigned to identical literal content reference a shared memory cell. If strings were mutable, changing one variable would corrupt fields globally across other decoupled threads.
  • 🔒
    Security Parameter Safety: Network sockets, database strings, and file system descriptors rely heavily on strings. Immutability prevents **Time-of-Check to Time-of-Use (TOCTOU)** race conditions where a string could be validated and then mutated right before kernel handover.
  • 🧵
    Thread Safety: String instances are implicitly thread-safe. They can be concurrently shared across worker pools without requiring heavy locks, synchronized wrappers, or deep volatile fencing.
🧠 Modifying the Backing Storage via Reflection
The Reflection Loophole: It is technically possible to break String immutability by altering the backing array (value[]) via deep reflection. However, this corrupts the String Pool globally and introduces massive data instability. In modern Java versions, the Java Platform Module System (JPMS) actively guards internal JDK fields and blocks this access at compile/runtime by default unless explicitly broken via command-line arguments.
Q 18
What is the Hashcode method used for in Java?
Java Collections

The hashCode() method computes an integer representation of an object's current state. Its core execution purpose is to serve as a high-velocity index key for distributing data partitions evenly across hash-based structures like HashMap and HashSet.

🤝 The Identity Contract with equals()
If objA.equals(objB) is evaluated to true, then objA.hashCode() must evaluate to the exact same integer output. If two objects provide identical hash codes, they are not guaranteed to be equal (this is a Hash Collision).
⚙️ Retrieval Architecture inside HashMaps
  • 🎯
    Bucket Apportionment: When looking up an entity, the map applies bit-shifting mechanics against the key's hash code to evaluate a specific storage bucket index in $O(1)$ time.
  • 🔀
    Collision Resolution: If multiple keys resolve to the same bucket index, Java stores nodes sequentially. In Java 8+, if a bucket's linked chain contains more than 8 collisions, it refactors the nodes into a balanced Red-Black Tree, limiting degradation to $O(\log n)$ rather than $O(n)$.
Q 19
Can a super class reference variable hold an object of a sub class?
Java

Yes, a superclass reference can point to a subclass instance on the heap. This mechanism is known as **Upcasting** and represents the foundational pillar for enabling **Runtime Polymorphism (Dynamic Method Binding)** in Java.

🛠️ The Compilation vs. Execution Boundary
The Reference Type dictates what methods are visible to the compiler at compile-time. The underlying Object Type determines how those methods behave at runtime via dynamic dispatch. 
class Vehicle { void start() { System.out.println("Vehicle moving"); } }
class Car extends Vehicle { @Override void start() { System.out.println("Car moving"); } }

Vehicle v = new Car();
v.start(); // Outputs "Car moving" (Runtime Polymorphism)
⚠️ Important Architect Trap: While method execution is polymorphic, **instance variables are not**. If a subclass redeclares a field defined in the superclass, the field is *hidden*, not overridden. Accessing the field via a superclass reference variable yields the parent's value, completely ignoring the subclass layout.
Q 20
Is multiple inheritance allowed in Java?
Java

No, Java explicitly disallows multiple inheritance using classes to completely avoid structural ambiguities like the Diamond Problem. However, Java allows a class to implement multiple interfaces, effectively supporting multiple inheritance of type and behavior.

💎 The Structural Threat: The Diamond Problem

If Class B and Class C both inherit from Class A, and both override an execute() method with different code layouts, letting Class D inherit from both B and C simultaneously leaves the compiler unable to reliably resolve which method body to dispatch at runtime.

⚙️ Default Method Conflict Resolution (Java 8+)

With default interface methods, conflict rules are strictly enforced:

  • 1
    Class implementation always wins over any default interface declaration.
  • 2
    If a class implements two separate interfaces declaring identical default signatures, the compiler halts with an assertion conflict. The developer must manually override the method and explicitly point out the target choice using InterfaceName.super.methodName().
Q 21
Can you explain a few tricky things about interfaces?
Java
1. The Variable Hiding Trap

All variables declared inside interfaces are implicitly compiled as public static final constants. They cannot be modified. Subclasses declaring matching variable identifiers merely hide them rather than overriding them.

2. Interface Method Return Type Deadlocks

If a class implements two interfaces containing methods with matching signatures but different primitive return types (e.g., int getData() vs String getData()), it creates a fatal compile-time collision that cannot be resolved in code.

3. Private Helpers & Stateless Constraints (Java 9+)

Java 9 allows private and private static methods inside interfaces to encapsulate boilerplate code across default methods. However, because interfaces cannot hold mutable instance fields, these helper methods must remain completely stateless.

Q 22
When do you use an abstract class?
Java

An abstract class should be used to establish a **partial architectural template** for tightly coupled subclasses. It acts as a structural foundation that allows sharing state and encapsulating common execution flows while forcing child variants to handle customized steps.

🎯 Primary Strategic Use Cases
  • 📋
    The Template Method Pattern: Define the immutable, overall skeletal workflow sequence as a final method in the abstract base, while declaring individual step variants as abstract methods for subclasses to complete.
  • 💾
    Managing Internal State: Interfaces are stateless. When your base class needs to manage mutable instance variables or leverage protected encapsulation boundaries, an abstract class is required.
  • 🧱
    Constructors & Common Lifecycles: While abstract classes cannot be directly instantiated via new, they can define constructors executed through super() down the instantiation chain to enforce unified lifecycle initialization across all subclasses.
Q 23
What is the use of this()?
Java

The this() statement triggers **Constructor Chaining** by invoking another constructor within the same class layout. Its core architectural goal is to eliminate code duplication across overloaded constructor blocks.

⚠️ Compilation Rules and Traps
  • 🛑
    Must Be First: The this() call must strictly occupy the very first line of code inside the constructor block. Any execution statement placed before it breaks compilation.
  • ❌
    Exclusive with super(): A constructor block can invoke this() or super(), but never both simultaneously, as both demand the absolute first execution slot.
  • 🔄
    No Recursive Loops: Cyclical constructor chaining (e.g., Constructor A calling B, and B calling A) is immediately detected and rejected by the compiler.
Q 24
What are the default values in an array?
Java

When an array is allocated on the heap, Java automatically seeds all index positions with predictable default values matching the array's declared data type. This guarantees type safety and blocks the reading of unallocated garbage memory locations.

💡 Senior Architect Warning: Conflating primitive arrays with object arrays creates dangerous runtime risks. Instantiating int[] defaults its indices to 0, whereas an array of object wrappers like Integer[] defaults entirely to null. Accessing indices on wrapper arrays without proper checks will cause implicit auto-unboxing, resulting in an immediate NullPointerException.
Q 25
What are best practices on garbage collection?
Java Concurrency
1. Align the GC Engine to Your Systems SLA

Favor G1GC for standard multi-gigabyte enterprise engines targeting balanced throughput with maximum pause delays under 200ms. Shift to **ZGC** for ultra-low latency requirements (e.g., streaming data, bots, real-time dashboards); ZGC completes its mark-and-sweep phases concurrently with application threads, keeping stop-the-world pauses below 1ms.

2. Curtail Allocation Pressures

Minimize garbage collection load by preventing unnecessary object creation: optimize primitive usage to avoid autoboxing inside hot loops, allocate arrays with explicit sizes to prevent internal data mirroring, and avoid calling System.gc().

3. Guard Against Long-Lived Reference Memory Leaks

Always invoke .remove() inside a finally block when managing context states using ThreadLocal. Ensure all application caches have strict eviction limits (like Caffeine or LRU mechanics) to prevent bounded memory pools from expanding into memory leaks, and routinely run entityManager.clear() during bulk batch database updates.

4. Container-Aware Heap Balancing

In cloud environments like Kubernetes, set your minimum heap size equal to your maximum size (-Xms = -Xmx) to eliminate dynamic runtime resizing. Ensure your configurations are container-aware so the JVM leaves an appropriate off-heap safety cushion (roughly 20-25%) for thread stacks and metaspace, protecting the cluster from abrupt container termination by the Linux OOM Killer.

Q 26
What are the important interfaces in the collection hierarchy?
Java Collections

The Java Collections Framework abstracts object grouping logic behind a unified interface hierarchy, segregating individual collections extending the Collection root from associative data pairings governed by the Map contract.

1. The Sequential Collection Tree
  • 🔹
    List: Extends Collection. Enforces a strict encounter order and permits duplicate entries. Provides indexed positional array access. Concrete classes include ArrayList and LinkedList.
  • 🔹
    Set: Extends Collection. Models unique mathematical constraints, explicitly prohibiting duplication. SortedSet and NavigableSet extensions arrange items using natural order or a custom Comparator. Concrete classes include HashSet and TreeSet.
  • 🔹
    Queue & Deque: Built to hold transient components prior to processing. Deque variants accept elements at both ends to serve as a FIFO Queue or a LIFO Stack (e.g., ArrayDeque).
2. The Sequenced Upgrades (Java 21 Core)

Java 21 introduced Sequenced Collections to standardize interactions with ordered data. Interfaces like SequencedCollection, SequencedSet, and SequencedMap provide clean, uniform accessors such as getFirst(), getLast(), and reversed().

3. The Associative Mapping Model

The Map interface handles structural lookup associations ($K \to V$). Keys must remain unique, while values can freely replicate. SortedMap and NavigableMap versions maintain ordered keys via a binary Red-Black tree structure (e.g., TreeMap).
