Q 03
What is a Job Worker in Camunda 8 and why is .send().join() used?
ZeebeSpring Boot@JobWorkergRPC

A Job Worker is a Spring component that subscribes to a specific job type in Zeebe and handles service task execution asynchronously over gRPC.

@Slf4j
@Component
public class BackgroundCheckWorker {

    @JobWorker(type = "backgroundCheck")
    public void handle(JobClient client, ActivatedJob job) {
        String name = (String) job.getVariablesAsMap().get("name");
        log.info("Running background check for: {}", name);

        client.newCompleteCommand(job.getKey())
              .variable("backgroundCheckPassed", true)
              .send().join();
    }
}
Why .send().join()?
  • 1️⃣
    newCompleteCommand(): Builds the request payload locally. No network I/O occurs.
  • 2️⃣
    .send(): Transmits the command asynchronously over gRPC stream and returns a ZeebeFuture.
  • 3️⃣
    .join(): Blocks the worker thread until Zeebe acknowledges the write. It ensures synchronous execution guarantees, proper exception handling, and prevents early worker thread release before confirmation.
Q 04
What happens if two Spring Boot apps run with identical Zeebe configs and @JobWorker names?
ZeebeScalingConcurrency

Zeebe treats both application instances as competing consumers and load-balances incoming jobs across them automatically via round-robin distribution.

┌───────────────────────────────┐ │ Zeebe Broker (:26500) │ └───────────────┬───────────────┘ │ ┌────────────────────┴────────────────────┐ │ Stream/Poll Jobs (type="backgroundCheck")│ ▼ ▼ ┌────────────────────┐ ┌────────────────────┐ │ Spring Boot App 1 │ │ Spring Boot App 2 │ │ Worker Instance A │ │ Worker Instance B │ └────────────────────┘ └────────────────────┘
Key Characteristics
FeatureBehavior
Horizontal ScalingIdentical codebases scale throughput seamlessly. Job #1 goes to App 1, Job #2 goes to App 2.
Exclusive LocksWhen Zeebe assigns a job to App 1, it sets a timeout lock. App 2 cannot process that job unless App 1 times out.
Accidental CollisionIf two different services share a job type name, jobs will be incorrectly split 50/50, causing runtime errors if App 2 lacks execution context.
Q 05
What is the Zeebe Broker and what benefits do you get by adding more brokers?
ZeebeClusterRaft ConsensusPartitioning

The Zeebe Broker is the core distributed execution engine of Camunda 8 that acts as the "brain" for workflow orchestration, maintaining process state logs via RocksDB and managing task allocations.

Benefits of Adding Broker Nodes
  • 🚀
    Increased Throughput (Horizontal Scaling): State is sharded into multiple partitions. Adding broker nodes allows partitions to spread across more hardware resources.
  • 🛡️
    High Availability & Fault Tolerance: Zeebe uses the Raft consensus algorithm with a configurable replication factor (e.g., 3). If a broker leader fails, a new leader is elected automatically without data loss.
  • ⚡
    No Database Bottleneck: Unlike C7 relational database lock contention, Zeebe brokers write to append-only logs, handling millions of process instances per day.
Q 06
What is Backpressure in Zeebe and how do you implement Exponential Backoff?
ResilienceBackpressureResilience4j

Backpressure is Zeebe's built-in safety mechanism. When the broker is overwhelmed, it rejects new commands with a RESOURCE_EXHAUSTED gRPC error rather than buffering requests indefinitely and causing OOM crashes.

Combining Backpressure & Exponential Backoff

When a worker catches RESOURCE_EXHAUSTED or downstream API failures, it applies an exponential delay (with jitter) before retrying to prevent retry storms.

@Bean
public RetryConfig apiRetryConfig() {
    return RetryConfig.custom()
        .maxAttempts(4)
        .intervalFunction(IntervalFunction.ofExponentialBackoff(500, 2.0)) // 500ms, 1s, 2s, 4s
        .retryExceptions(ResourceExhaustedException.class, IOException.class)
        .build();
}
Q 07
How do you process 10,000 orders efficiently in Camunda 8?
High ThroughputMulti-InstanceScaling
  • 1️⃣
    Parallel Multi-Instance Subprocess: Spawn individual tokens for each item across cluster partitions dynamically instead of sequential looping.
  • 2️⃣
    Worker Horizontal Scaling: Scale Spring Boot worker pods on Kubernetes. Set maxJobsActive=64 or higher to maximize throughput per worker thread pool.
  • 3️⃣
    Partition Tuning: Ensure the Zeebe cluster has sufficient partitions (e.g., 8–16) to distribute the multi-instance job load across broker nodes.
  • 4️⃣
    Worker Idempotency: Ensure downstream database updates check order state before applying changes to safely handle gRPC retries.

  • Cancels the target task immediately

  • Used for critical error handling / aborts

Q 13
What is Asynchronous Continuation in Camunda (Async Before / Async After)?
Camunda PlatformZeebeFlow Control

Asynchronous Continuation introduces explicit **state savepoints** into a process diagram, committing variables to persistent storage and splitting execution into separate transaction boundaries.

  • 🔷
    asyncBefore = true: Engine pauses before executing the task, commits variables, and pushes a job log. If execution fails, rollback stops at this boundary, protecting prior steps.
  • 🔶
    asyncAfter = true: Engine executes the task logic, then forces a hard state commit before passing the token downstream, ensuring side effects (e.g., bank payout) are saved.
Q 14
How does BPMN Compensation work in Camunda 8? (E-Commerce Example)
CompensationBPMN EventsSaga

Compensation is an undo pattern used to revert tasks that have already completed successfully when a downstream step fails.

1. Execution & Registration: [Payment ✅] ──▶ Zeebe registers Compensation Boundary Event (Revert Payment) [Inventory Check ✅] ──▶ Zeebe registers Compensation Boundary Event (Update Inventory) 2. Failure & Error Catch: [Shipping ❌] worker calls client.newThrowErrorCommand("SHIPMENT_FAILED") Error Boundary Event catches error ──▶ Routes token to 🔄 Compensation Throw Event 3. LIFO Compensation Execution: Zeebe executes compensating handlers in reverse order of completion: 1. cancelOrder worker 2. revertPayment worker 3. updateInventory worker
Q 15
How is a Compensation Event triggered from a @JobWorker?
JobWorkerCompensation

A worker never triggers compensation directly via API. Instead, the worker signals a business failure, and BPMN routes the token into a Compensation Throw Event.

@JobWorker(type = "processShipping")
public void handleShipping(JobClient client, ActivatedJob job) {
    boolean success = shippingService.arrangeDelivery(...);

    if (!success) {
        // Step 1: Throw BPMN Error to redirect token to Compensation Throw Event
        client.newThrowErrorCommand(job.getKey())
              .errorCode("SHIPMENT_FAILED")
              .errorMessage("Courier service unavailable")
              .send().join();
    } else {
        client.newCompleteCommand(job.getKey()).send().join();
    }
}
Q 16
What is the Saga Pattern? (Choreography vs Orchestration)
MicroservicesSagaDistributed Transactions

The Saga pattern manages data consistency across distributed microservices without distributed ACID transactions by executing local transactions followed by compensating transactions on failure.

📡 Choreography

  • Services listen to events and decide next steps
  • No central point of control
  • Hard to monitor complex workflows

🎯 Orchestration (Camunda 8)

  • Camunda engine acts as central coordinator
  • Tracks state log and triggers compensation
  • Full visibility via Operate dashboard

Q 24
What is JTA and why doesn't Camunda 8 support it?
TransactionsJTAArchitecture

JTA (Java Transaction API) manages distributed transactions across a shared relational database in embedded Java engines. Camunda 8 decouples Zeebe over gRPC network boundaries, making atomic JTA rollbacks physically impossible across network hops. Architecture relies on Idempotency instead.

Q 25
Idempotency Pattern in Camunda 8
ReliabilityZeebe Retry
@JobWorker(type = "save-order-item")
public void handleItemSave(JobClient client, ActivatedJob job) {
    String itemId = (String) job.getVariablesAsMap().get("itemId");

    // Idempotency check: Skip duplicate insert on Zeebe retry
    if (!orderItemRepository.existsById(itemId)) {
        orderItemService.saveItem(...);
    }

    // Always complete job
    client.newCompleteCommand(job.getKey()).send().join();
}

Q 30
What are the Key Challenges & Steps when Migrating from Camunda 7 to 8?
MigrationRefactoring
  • 1️⃣
    Finish-in-Place Strategy: Active C7 instances complete on C7; new processes launch on C8. Database migration is not possible due to RocksDB log architecture.
  • 2️⃣
    JavaDelegate Refactoring: Convert in-memory delegates to remote @JobWorker microservices over gRPC.
  • 3️⃣
    Transaction Redesign: Replace JTA ACID transactions with Idempotency checks and Saga Compensations.
  • 4️⃣
    FEEL Expressions: Rewrite Groovy/JUEL scripts to standard FEEL syntax.
Q 31
Process Versioning & How to Migrate Active In-Flight Instances
VersioningMigration API

Default Behavior: Existing instances remain pinned to the process definition version they started on. Deploying Version 2 only affects newly created process instances.

In-Flight Migration: To force running instances to move to a new definition version, create a MigrationPlan mapping activity token IDs from source version to target version, then execute via Operate or Zeebe Migration API.

Q 37
How do you design a DMN Decision from scratch in Camunda Modeler?
DMNCamunda ModelerDecision Table
  1. Open Modeler ➔ New DMN ➔ Target Camunda Cloud (Camunda 8).
  2. Set Diagram ID = Definitions_Eligibility and Name = Eligibility.
  3. Drag a Decision box onto canvas. Set ID = Decision_Eligibility (must match BPMN calledDecision).
  4. Double-click Decision box to switch to Decision Table View. Set Hit Policy = FIRST.
  5. Configure Input column: Label = Age, Expression = age, Type = integer.
  6. Configure Output column: Label = Eligible, Name = eligibility, Type = boolean.
  7. Add Rows (Rules): < 18 ➔ false, > 60 ➔ false, [18..60] ➔ true.
  8. Save file as eligibility.dmn in project classpath.
