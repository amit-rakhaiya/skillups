Q 02
Camunda Cloud (SaaS) vs Self-Managed
DeploymentZeebe

☁️ Camunda Cloud (SaaS)

  • Fully managed by Camunda on AWS
  • Zero infrastructure setup
  • Zeebe, Operate, Tasklist, Optimize hosted
  • Connect via client credentials (OAuth)
  • Best for: quick start, no ops team

🖥️ Self-Managed

  • You run Zeebe + all apps on Kubernetes
  • Helm charts provided by Camunda
  • Full control over data & scaling
  • Can run locally (dev) without Docker
  • Best for: enterprise, compliance, on-prem
💡 Our POC: Self-Managed locally — Zeebe on port 26500, Operate/Tasklist on 8080, Spring Boot app on 8082.

Q 05
What is a Job Worker in Camunda 8?
ZeebeSpring Boot@JobWorker

A Job Worker is a Spring component that subscribes to a specific job type in Zeebe and handles service task execution.

@Slf4j
@Component
public class BackgroundCheckWorker {

    @JobWorker(type = "backgroundCheck")
    public void handle(JobClient client, ActivatedJob job) {
        String name = (String) job.getVariablesAsMap().get("name");
        log.info("Running background check for: {}", name);

        client.newCompleteCommand(job.getKey())
              .variable("backgroundCheckPassed", true)
              .send().join();
    }
}
ConceptDetail
Importio.camunda.zeebe.spring.client.annotation.JobWorker
typeMust match service task type in BPMN
ActivatedJobContains job key, variables, process info
Must always callnewCompleteCommand() or newFailCommand()
Without completeZeebe retries indefinitely

Q 07
How many ways can you start a Camunda 8 process?
Process Instantiation
  • 1️⃣
    None Start Event — Triggered via ZeebeClient API: newCreateInstanceCommand().bpmnProcessId(...).send()
  • 2️⃣
    Timer Start Event — Auto-start on schedule. Use timeDuration for delay or timeCycle for recurring (cron-like).
  • 3️⃣
    Message Start Event — Starts when a named message arrives: newPublishMessageCommand().messageName("loan-received")
  • 4️⃣
    Signal Start Event — Broadcast signal starts multiple process instances simultaneously.
  • 5️⃣
    REST API (Zeebe Gateway) — POST /v1/process-instances with process ID and variables.
  • 6️⃣
    Camunda Tasklist / Operate UI — Manually start from UI for testing.
  • 7️⃣
    Form-linked Start (Tasklist) — User fills a start form in Tasklist, submit triggers process start with form variables.
  • 8️⃣
    Call Activity — Parent process instantiates child process via <callActivity calledElement="...">
  • 9️⃣
    Event Sub-process — Triggered by timer/message/signal/error event within a running process scope.
💡 Our POC: None Start Event — Tasklist renders person.form, on submit Zeebe API starts the process with form variables.

Q 09
User Task vs Manual Task
BPMN Tasks

👤 User Task

  • System-assisted human task
  • Appears in Tasklist for assignment
  • Linked to a Form (Camunda Form or external)
  • Variables captured on form submit
  • Can have task listeners
  • Example: Manager reviews loan application

✋ Manual Task

  • Completely offline human work
  • No system interaction whatsoever
  • Does NOT appear in Tasklist
  • No form, no variables captured
  • Process continues automatically
  • Example: Print and file a paper document
Q 10
Gateways in BPMN — All Types Explained
BPMNGatewayFlow Control
GatewaySymbolSplit behaviourJoin behaviour
XOR (Exclusive)✕ or ◇Exactly ONE path fires (first matching condition)Passes first arriving token
AND (Parallel)+ALL paths fire simultaneouslyWaits for ALL incoming tokens
OR (Inclusive)◯ONE or MORE paths fire based on conditionsWaits for all active paths
Event-Based⬡Waits for first event (timer/message) to occurN/A (catching only)
🔍 XOR vs OR — Common Interview Trap
XOR: 3 paths, conditions: A=true, B=true, C=false → Only ONE fires → Path A wins (first matching) OR: 3 paths, conditions: A=true, B=true, C=false → BOTH A and B fire → two parallel tokens → OR join waits for both to complete
📌 Event-Based Gateway
Process reaches Event-Based Gateway │ ├── ⏱️ Timer (3 days) ─── no response received └── 📨 Message ──────── payment confirmed Whichever fires FIRST wins → other is cancelled
💡 In our POC: XOR gateway after Eligibility Check (routes on eligibility=true/false). AND split runs Manager Review + Background Check in parallel. XOR merge before AND join collapses escalation/normal paths to avoid deadlock.

DMNBusiness RulesFEEL

DMN is a standard for defining business rule decisions as tables, separate from process flow. Evaluated via a Business Rule Task in BPMN.

Our eligibility.dmn

FIRST< 18false

[18..60]true

  • Token leaves task via boundary flow
  • Task cannot complete normally

Q 15
Sub-process & Escalation Pattern — Deep Dive
Sub-processEscalationPOC
🔗 How Escalation connects sub-process to parent
Shared escalation definition: <bpmn:escalation id="Escalation_ManagerEscalation" escalationCode="MANAGER_ESCALATION"/> Inside sub-process: <bpmn:endEvent> <bpmn:escalationEventDefinition escalationRef="Escalation_ManagerEscalation"/> </bpmn:endEvent> ↑ throws MANAGER_ESCALATION upward, terminates sub-process On sub-process boundary (parent): <bpmn:boundaryEvent attachedToRef="SubProcess_ManagerReview"> <bpmn:escalationEventDefinition escalationRef="Escalation_ManagerEscalation"/> </bpmn:boundaryEvent> ↑ catches it → continues to Notify Senior Manager
🗺️ Full Flow in our POC
AND Split ├── SubProcess_ManagerReview │ Inside: │ SubStart → Manager Review (User Task) │ │ │ └── ⏱️ 2-min Interrupting Timer │ ↓ │ Escalation End Event (MANAGER_ESCALATION) │ ↓ throws upward │ On boundary: │ Escalation Boundary catches MANAGER_ESCALATION │ ↓ │ Notify Senior Manager (notify-senior-manager worker) │ ↓ │ XOR Merge ← also receives flow from normal sub-process end │ ↓ └── Background Check → AND Join ↓ Process End
💡 Why XOR Merge before AND Join? AND join counts ALL declared incoming flows. Without XOR merge, escalation path AND normal path both point to AND join — if escalation fires, normal path never sends its token → deadlock. XOR merge collapses both into one token.

Q 17
Process Instance Variable vs Multi-Instance Variable
VariablesMulti-Instance

📌 Process Instance Variable

  • One value, shared across entire process
  • Visible to all tasks globally
  • Set at start or by any worker
  • Example: name, email, eligibility

🔁 Multi-Instance Variable

  • Each iteration has own local scope
  • inputElement: current item (local)
  • outputElement: result collected to array
  • Example: verify each document in parallel
<zeebe:loopCharacteristics
  isSequential="false"
  inputCollection="=documents"
  inputElement="document"
  outputCollection="results"
  outputElement="=verified"/>

Q 18
What is JTA and why doesn't Camunda 8 support it?
TransactionsJTAArchitecture

JTA (Java Transaction API) provides distributed transactions across multiple resources (DB + JMS + etc.) in a single ACID boundary.

Camunda 7 — JTA works
@Transactional  // ONE transaction covers both
public void saveAndComplete(PersonEntity person, DelegateExecution exec) {
    personRepo.save(person);         // DB write
    exec.setVariable("saved", true); // Engine write (same DB)
    // crash here → BOTH roll back ✅
}
Camunda 8 — JTA impossible
@JobWorker(type = "save-person-info")
public void handle(JobClient client, ActivatedJob job) {
    personRepo.save(person);  // DB write ✅
    // app crashes 💥
    client.newCompleteCommand(job.getKey()).send().join(); // never called
    // Zeebe retries → duplicate insert ❌
}

Zeebe communicates via gRPC over a network boundary — JTA cannot span across a network. Solution: Idempotency pattern.

Q 19
Idempotency Pattern in Camunda 8
ReliabilityZeebe RetryPOC

Problem: Zeebe retries a job if the worker saves to DB but crashes before calling newCompleteCommand() — causes duplicate inserts.

@JobWorker(type = "save-person-info")
public void handlePersonInfo(JobClient client, ActivatedJob job) {
    String email = (String) variables.get("email");

    // IDEMPOTENCY CHECK — skip if already saved (retry scenario)
    if (personRepository.existsByEmail(email)) {
        log.warn("Already exists, skipping — likely a Zeebe retry.");
    } else {
        PersonEntity person = PersonEntity.builder()
            .name((String) variables.get("name"))
            .email(email)
            // ... other fields
            .build();
        personService.savePerson(person);
    }

    // Always complete — regardless of save or skip
    client.newCompleteCommand(job.getKey()).send().join();
}
💡 Rule: Always complete the job. Without it, Zeebe retries indefinitely. Idempotency ensures retries are safe.

Q 23
Business Objects — Does Camunda support them?
VariablesJSONPOC

Yes — pass entire object as a JSON variable instead of individual fields. Camunda 8 speaks JSON natively (no Java serialization like Camunda 7's ObjectValue).

// Instead of 9 individual variables — pass one object:
@JobWorker(type = "save-person-info")
public void handle(JobClient client, ActivatedJob job) {
    // Auto-deserialize all variables into Person record
    Person person = job.getVariablesAsType(Person.class);
    personService.savePerson(toEntity(person));
    client.newCompleteCommand(job.getKey()).send().join();
}

Note: Camunda Forms flatten fields as individual variables. You can re-aggregate them in a worker or use a mapping gateway step.

Process Lifecycle
